# Threat Model: bee

## 1. System context

bee is a Rust workspace that gives AI coding-agent tools capability-scoped access to a Linux host. Its security-critical path parses declarative policy, proves child-policy attenuation, resolves host identities and destinations, builds an eBPF-specific `EnforcementPlan`, attaches BPF LSM programs, creates a cgroup per scope, and enforces file-open, executable, and IP-connect decisions in the kernel.

The workspace also includes a harness for prompts, external model providers, built-in shell/file tools, local and remote MCP servers, transcripts and audit, CTF evaluation, in-process rendering, and work-in-progress `SKILL.md` discovery and capability grants. Intended users are agent operators, framework integrators, and evaluation researchers. Production enforcement requires Linux BPF LSM/BTF/cgroup v2 and a privileged loader; the default harness build is process-hardened and credential-stripped but not kernel-confined. This analysis covers the current dirty worktree, including uncommitted skill support.

## 6. Open questions

- Is the default host-only harness ever used for real or untrusted agents, or only for tests and trusted smoke runs?
- In production, does the workload child run as an unprivileged uid with no ambient/inheritable capabilities, or does it inherit the privileged loader identity?
- Are unmatched filesystem reads, conditional unmatched-write behavior, observe mode, hard-link aliases, and bind-mount aliases intentional and acceptable for production policies?
- Are repository-supplied scenario/provider files trusted, or should their pre-sandbox filesystem writes, provider origins, and secret env-var selection require operator approval?
- Are remote MCP servers fully trusted after hostname gating? Are redirects followed, are resolved private/loopback addresses allowed, and is DNS revalidated after connection?
- Which model-provider endpoints and credential env-var names are authorized, and what data may be sent to them?
- Where are transcripts, metrics, and audit logs persisted; who can read them; how long are they retained; and must secrets be redacted?
- Is observe mode permitted in production or only during policy development?
- Will production skill discovery include repository and user-global roots? What provenance/signing, shadowing warning, consent UX, and grant persistence are intended?
- Must enforcement-feature checks and the live BPF-LSM VM matrix block merges or releases?
- Will bee run inside containers or shared cgroup hierarchies, and who owns the parent cgroup and lifecycle cleanup?
- Is the configured VM test target trusted enough to disable SSH host-key verification before executing copied artifacts with sudo?
